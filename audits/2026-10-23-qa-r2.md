## Blockers

### QA-017: First-run setup fails, and one failed attempt permanently blocks it (orphaned Carrier "AV")
- **Area:** onboarding
- **URL:** https://openfront-airline-production.up.railway.app/dashboard/init
- **Steps:**
  1. On the empty production database, open `/dashboard/init`.
  2. Submit Name "QA Operator", Email `qa@openship.org`, Password `short`. This is rejected as expected, with "ERROR Unable to create the initial user. Please try again."
  3. Submit again with a valid 16+ character random password.
  4. Query `{ publicCarrierIdentity(carrierCode:"AV") { name storefrontConfigured } }` and `{ redirectToInit }` on `/api/graphql`.
- **Expected:**
  - Step 2 is rejected with nothing written.
  - Step 3 creates the operator, their Carrier and the full-permission Role, then signs in and lands on onboarding.
- **Actual:**
  - Step 3 also fails with the same generic message. Sending the same `createInitialUser` mutation directly returns `KS_PRISMA_ERROR`: "Invalid `prisma.user.create()` invocation … `carrier: { connect: { id: undefined …`".
  - Step 4 returns the carrier `{"name":"Avante Air","storefrontConfigured":false}` while `redirectToInit` is still `true`, so a Carrier exists with zero users.
  - Every later attempt fails, so the product can never be set up from the UI.
- **Cause:**
  - `initFirstItem.itemData` nests `carrier: { create: { code: "AV", … } }` and `role: { create: … }`. Keystone resolves nested relationship creates before the User's `validate` hook runs.
  - The 16-character rule in `User.hooks.validate` (and `password` `length.min`/`rejectCommon`) therefore rejects the User after the Carrier "AV" (and probably the Role) have already been committed. Nested creates are not transactional.
  - On every later attempt, the nested Carrier create hits the unique `Carrier.code` index, the nested create yields no id, and the user insert fails with `connect: { id: undefined }`.
  - E-commerce doesn't hit this because it nests only a Role, which has no unique field.
- **Fix direction:**
  - Create carrier, role and user in one transaction, as `scripts/bootstrap-production.ts` already does, for example with a custom init mutation.
  - Or validate the password before any nested write.
  - Or attach to an existing user-less carrier rather than creating one.
  - Production's orphan Carrier "AV" (and any orphan Role) needs clearing, or reusing, before setup can complete.
- **Likely files:**
  - `features/keystone/index.ts:41-62` (`initFirstItem.itemData`)
  - `features/keystone/models/User.ts` (`hooks.validate`, the `password` validation)
  - `features/keystone/models/Carrier.ts:31` (unique `code`)
  - `features/keystone/lib/initial-operator-setup.ts`

## Major

### QA-018: The init form hides why it failed and never states the 16-character password rule
- **Area:** onboarding
- **URL:** `/dashboard/init`
- **Steps:**
  1. Open `/dashboard/init` and look at the Password field.
  2. Submit a short or common password, or an invalid email.
- **Expected:**
  - The form says up front that the password needs at least 16 characters.
  - Each error names the real problem. Keystone already returns "The initial operator password must contain at least 16 characters.", "value is too common", "Enter a valid operator email address."
- **Actual:**
  - There is no hint text and no `minLength`.
  - Every failure, including the server Prisma error in QA-017, shows the same "ERROR Unable to create the initial user. Please try again."
  - "Try again" is wrong advice when retrying can never succeed (QA-017).
  - The operator has no way to know a 16-character password is needed. A first short attempt is exactly what triggers QA-017.
- **Likely files:**
  - `features/dashboard/actions/auth.ts:96-102` (`createInitialUser` discards `response.error`)
  - `features/dashboard/screens/InitPage/index.tsx` (no password hint)
  - **Parity note:** the generic message comes from the shared shell. Airline's 16-character rule is stricter than E-commerce's, so the hint at least is Airline's job.

## Minor

### QA-019: `robots.txt` and `sitemap.xml` redirect to `/dashboard/init` while setup is pending
- **Area:** storefront
- **URL:** `/robots.txt`, `/sitemap.xml`
- **Steps:** `curl -I` both on the current production.
- **Expected:** `robots.txt` always returns text that disallows `/dashboard`, so a crawler never indexes the admin-creation page.
- **Actual:**
  - Both return 307 to `/dashboard/init`, an indexable page that lets anyone create the first admin.
  - The proxy matcher doesn't exclude `robots.txt` or `sitemap.xml`. E-commerce has the same proxy.
- **Likely file:** `proxy.ts` (`config.matcher` and the `redirectToInit` branch)

### QA-020: GraphQL introspection is enabled on production
- **Area:** dashboard (API)
- **URL:** `/api/graphql`
- **Steps:** POST `{ __schema { queryType { name } } }` with no session.
- **Expected:** Introspection is off in production, or this is a deliberate parity choice.
- **Actual:**
  - Returns `{"data":{"__schema":{"queryType":{"name":"Query"}}}}`.
  - The whole operator schema is mapped for anyone: refunds, travel documents, machine credentials.
  - Low risk, since access control holds (anonymous `carriers` and `users` are empty), but worth a decision. Check E-commerce for parity before changing.
- **Likely file:** `features/keystone/index.ts` (`graphql` config)

### QA-021: The init page title is "Openfront Dashboard" on what is, for now, the whole public site
- **Area:** onboarding
- **URL:** every path while no user exists
- **Steps:** Open `/` on production.
- **Expected:** A neutral setup title. Ideally the public storefront paths show the "Online booking isn't available yet" frame from round-1 QA-002 instead of an admin-creation form.
- **Actual:** Customers who visit the airline's URL before setup land on "Create admin account". Shared-proxy behaviour (same as E-commerce), so this is an owner decision rather than an Airline bug.
- **Likely file:** `proxy.ts:13-15`

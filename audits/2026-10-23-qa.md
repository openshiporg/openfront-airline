## Blockers

### QA-001: First-run operator setup is impossible on production (no admin can ever be created)
- **Area:** onboarding
- **URL:** https://openfront-airline-production.up.railway.app/dashboard/init
- **Steps:**
  1. Open `/dashboard/init` on the fresh production install.
  2. Open `/dashboard`.
  3. Query `{ redirectToInit }` on `/api/graphql`.
- **Expected:** As in E-commerce, an empty database sends `/dashboard` to `/dashboard/init`, and the first-user form creates the admin.
- **Actual:**
  - `/dashboard/init` returns 307 to `/dashboard`, then 307 to `/dashboard/signin?from=%2Fdashboard`.
  - `redirectToInit` returns `false`.
  - `/dashboard/signup` also redirects to sign-in, because `PUBLIC_SIGNUPS_ALLOWED` is unset.
  - There is no route at all to a first account, so the product can't be onboarded, the dashboard can't be QA'd and the storefront can never be configured.
- **Cause:** `initialOperatorSetupEnabled()` returns false when `NODE_ENV=production` unless `ALLOW_INITIAL_OPERATOR_SETUP=true`. Production only has the seven standard variables (`DATABASE_URL`, `SESSION_SECRET`, `S3_*`). E-commerce's `redirectToInit` only checks `User.count === 0`. Already flagged as owner decision #1 in `~/Code/Euler/state/qa-loop/batches3-6/airline-REDESIGN-READY.md`.
- **Likely files:**
  - `features/keystone/lib/initial-operator-setup.ts:1-3`
  - `features/keystone/mutations/redirectToInit.ts:9`
  - `features/keystone/index.ts:44` (`initFirstItem` gated)
  - `features/storefront/lib/carrier.ts:41`, which also throws in production when init is disabled and the carrier query fails

### QA-002: Every storefront page, including Help, Contact and Flight status, is a dead end with no navigation
- **Area:** storefront
- **URL:** `/`, `/status`, `/help`, `/contact`, `/manage-booking`, `/check-in`
- **Steps:** Open any storefront route on production at 390px or 1440px.
- **Expected:**
  - Static pages (Help, Contact) still render, with the carrier header and footer.
  - The unconfigured notice has a way forward: for an operator, a "Set up" or "Dashboard" link; for a traveller, contact info.
  - Status, Manage booking and Check-in show their own fallback notices, which already exist in the code ("Flight status isn't available right now.", and so on).
- **Actual:**
  - All six routes render the identical full-screen "FLIGHTS / ONLINE BOOKING ISN'T AVAILABLE YET / Try again" card.
  - The page has no header, no footer, no nav and no `<header>`/`<footer>` landmarks.
  - "Try again" links to `/`, which shows the same page.
  - The per-page fallback messages in `app/status/page.tsx`, `app/manage-booking/page.tsx` and `app/check-in/page.tsx` are unreachable, because `PublicPageShell` returns `<UnconfiguredStorefront />` first.
  - `/help` and `/contact` don't need a carrier, but are blanked anyway.
  - Blocker for day one because, combined with QA-001, this is the only thing the public can ever see.
- **Likely files:**
  - `features/storefront/components/PublicPageShell.tsx:17`
  - `features/storefront/components/StorefrontChrome.tsx:71-81`

## Major

### QA-003: Password reset can never send email in production, so an operator who forgets their password is locked out
- **Area:** dashboard (auth)
- **URL:** https://openfront-airline-production.up.railway.app/dashboard/reset
- **Steps:** Request a reset for an existing operator's email on production.
- **Expected:** A reset email is sent, or the operator is told email isn't configured.
- **Actual** *(code; I couldn't reproduce live because no user exists)*:
  - `sendPasswordResetEmail` throws "Complete SMTP configuration is required in production." when any of `SMTP_HOST`, `SMTP_FROM`, `SMTP_USER`, `SMTP_PASSWORD` or `SMTP_PORT` is missing. `getBaseUrlForEmails` also throws without `SMTP_STORE_LINK`.
  - None of these are set on production. The user gets the generic "Unable to reset your password. Please try again."
  - E-commerce's `mail.ts` warns and continues instead of throwing.
  - For an unknown email, the UI shows "SUCCESS Password reset link has been sent to your email." (verified live with `qa@openship.org`).
- **Likely files:**
  - `features/keystone/lib/mail.ts:9`
  - `features/keystone/lib/mail.ts:79-81`
  - `features/dashboard/actions/auth.ts:122-127`

### QA-004: No online payment: bookings are "reservation only, pay the airline directly"
- **Area:** storefront
- **URL:** `/` (search console), booking confirmation
- **Steps** *(code)*: Book a flight.
- **Expected:**
  - An airline storefront takes payment at booking.
  - E-commerce has Stripe checkout, and this repo already has `PaymentProvider`, `PaymentSession` and `features/integrations/payment/process-webhook.ts`.
  - The brief asks for Stripe test-mode checkout wherever it exists.
- **Actual:**
  - The console states "Reservation only · Pay the airline directly · Unpaid holds expire in 24 h".
  - The confirm step says "No online payment".
  - The booking stays "Awaiting payment", and seat selection is locked until `paymentStatus === 'paid'`.
  - So a traveller who books online can't choose a seat or check in until staff mark the booking paid.
- **Likely files:** `features/storefront/components/FlightShop.tsx:259`, `:317`, `:345`, `:60-63`

### QA-005: Only one-way trips for adults 18+ can be booked
- **Area:** storefront
- **URL:** `/`
- **Steps** *(code)*: Open the search console.
- **Expected:** At minimum, round trip, plus children and infants. These are day-one requirements for any carrier selling direct.
- **Actual:**
  - Single origin, destination and date.
  - The only passenger selector is "Adults 18+" (1–9).
  - Date of birth is capped at 18 years before departure.
  - Families can't book.
- **Likely file:** `features/storefront/components/FlightShop.tsx:253-259`, `:309`

### QA-006: No booking confirmation email; the long access code is shown once and can't be recovered
- **Area:** storefront
- **URL:** the booking confirmation pass; `/manage-booking`; `/check-in`
- **Steps** *(code)*: Confirm a reservation.
- **Expected:**
  - The traveller gets an email with the booking reference and access details, as E-commerce sends order confirmations.
  - There's a self-service way to recover access by booking reference plus surname or email.
- **Actual:**
  - `features/keystone/lib/mail.ts` only has `sendPasswordResetEmail`.
  - The confirmation shows a long opaque token with a "Copy access code" button.
  - Manage booking and check-in require both the reference and that token; the token field is `type="password"`.
  - Losing the tab means losing self-service access.
  - There are no customer accounts or booking history (the brief's "account sign-up and sign-in" and "order history" don't exist for travellers).
- **Likely files:**
  - `features/storefront/components/FlightShop.tsx:268-282`, `:325-326`
  - `features/keystone/lib/mail.ts`

### QA-007: Search defaults to JFK → BOS regardless of the carrier's network
- **Area:** storefront
- **URL:** `/`
- **Steps** *(code)*: Load the home page.
- **Expected:** Origin and destination default to empty, or to the carrier's own airports. Ideally there's an airport picker fed by the carrier's `Route` and `Airport` records.
- **Actual:**
  - `defaultValue="JFK"` and `defaultValue="BOS"` are hard-coded placeholder data.
  - The fields are free-text 3-character codes with no lookup.
  - A carrier that doesn't fly JFK–BOS shows "no flights" on the first search.
- **Likely file:** `features/storefront/components/FlightShop.tsx:253-254`

### QA-008: Station travel-document registration fails on production
- **Area:** dashboard
- **URL:** `/dashboard/platform/departures` (gate-agent document action)
- **Steps** *(code and the redesign handoff; couldn't reach it live)*: Register a passenger's travel document at the gate.
- **Expected:** The document is tokenized and saved.
- **Actual:**
  - Without `TRAVEL_DOCUMENT_TOKENIZATION_KEY`, which production doesn't have, the command returns "Travel-document tokenization is not configured."

  - Owner decision #2 in `airline-REDESIGN-READY.md`.
